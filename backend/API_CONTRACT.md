# Системное описание модуля контроля доступа (RBAC)

## 1. Алгоритм работы (Расчет эффективных прав)

Когда авторизованный пользователь пытается совершить действие (например, зайти в раздел или нажать кнопку), система рассчитывает его итоговые (эффективные) права по следующему пошаговому алгоритму:

ШАГ 1: Получить ID текущего пользователя из сессии/токена.

ШАГ 2: Найти все роли, которые напрямую привязаны к данному пользователю в таблице связей.

ШАГ 3: Для каждой найденной роли запустить рекурсивный обход вверх по дереву иерархии (через поле parent_id), чтобы собрать полную цепочку всех родительских ролей.

ШАГ 4: Сделать запрос в матрицу прав по всем собранным ролям для запрашиваемого Действия и Раздела.

ШАГ 5 (Развилка конфликтов):

ЕСЛИ среди найденных записей в матрице есть хотя бы одна запись с типом access_type = 'deny',

-> ТО эффективное право получает статус Запрещено (false). Алгоритм завершается (Приоритет запрета).

->ИНАЧЕ (если явных запретов deny не обнаружено):

->-> ЕСЛИ есть хотя бы одна запись с типом access_type = 'allow',

-- ТО эффективное право получает статус Разрешено (true).

-- ИНАЧЕ (если для действия нет ни разрешений, ни запретов)ТО право получает статус Запрещено (false) (принцип закрытого соглашения — по умолчанию всё запрещено).

## 2. Типы данных (Поля базы данных) Ниже приведена системная таблица всех полей, используемых в наших 6 таблицах базы данных PostgreSQL.

7 users_roles.user_id BigInteger (FK) Ссылка на users.id в промежуточной таблице 

8 users_roles.role_id Integer (FK) Ссылка на roles.id в промежуточной таблице 

9 app_sections.idInteger (PK)Уникальный ID раздела приложения

12 app_permissions.section_id Integer (FK)Ссылка на app_sections.id (раздел действия)

## 3. Преобразования (Data Transformation) Таблица показывает, как сырые строки из базы данных на Бэкенде трансформируются через Python-логику (DRF) в готовый JSON-контракт для Фронтенда.

Исходные поля и типы (Бэкенд / БД) || Правило преобразования (Бэкенд-логика) || Итоговые поля и типы (Фронтенд / JSON)

app_sections.slug (Varchar) || Становится главным ключом первого уровня в JSON-объекте. || key (String) — название объекта раздела.

app_permissions.codename (Varchar) || Становится вложенным ключом внутри своего раздела. || key (String) — название свойства действия.

matrix.access_type (Varchar) || Проходит через алгоритм ЕСЛИ/ТО (расчет эффективных прав по иерархии). Превращается в булево значение. || value (Boolean) — true (если разрешено) или false (если запрещено).


## Наглядный формат общения с фронтом (преобразования)

Просмотр логов аудита (Для Админов и Аудиторов)
* **ЕСЛИ** фронтенд делает запрос `GET /api/admin/audit-logs/` (с токеном админа),
* **ТО** бэкенд забирает данные из таблицы `audit_logs` (благодаря db_index сортировка по дате будет мгновенной) и возвращает статус `200 OK` в виде списка:
  ```json
  [
    {
      "id": 154,
      "username": "vasya",
      "action": "blog:delete",
      "result": "deny",
      "created_at": "2026-06-16T18:30:00Z"
    }
  ]
  ```

Получение полной матрицы прав (Для экрана управления «Роль × Право»)
* **ЕСЛИ** фронтенд делает запрос `GET /api/admin/matrix/`,
* **ТО** бэкенд трансформирует каталог прав и связи в формат нашей идеи для удобной отрисовки таблицы:
  ```json
  [
    {
      "permission_id": 42,
      "section": "blog",
      "action": "delete",
      "roles_assigned": {
        "Administrator": "allow",
        "Manager": "allow",
        "Intern": "deny"
      }
    }
  ]
  ```

* **ЕСЛИ** фронтенд делает запрос `GET /api/v1/users/me/permissions/`,  
* **ТО** :
```json
[
{
  "analytics": {
    "view": true,
    "export": false
  },
  "blog": {
    "view": true,
    "create": true,
    "delete": false
  }
}]

```
