### Этап 4. Переход на реальный API

Когда Виталик сказал, что бэкенд готов, я проверил репозиторий и выяснил:

- API лежит в ветке `feat/back-models-filling`, а не в `development`;
- формат ответов **отличается** от того, что я закладывал изначально;

**Что сделал на фронте:**

1. **Удалил mock** — приложение теперь работает только с бэкендом.
2. **Переделал авторизацию:**
   - раньше планировались cookie + CSRF;
   - бэкенд отдаёт **Token** → сохраняю в `localStorage`, шлю в заголовке `Authorization: Token ...`.
3. **Переделал матрицу:**
   - GET возвращает плоский список `{ role_id, permission_id, grant }`, а не готовую таблицу;
   - POST принимает `{ changes: [...] }`, а не всю матрицу целиком;
   - роли и названия прав взял из `init_data.json` бэкенда (каталог на фронте), потому что отдельного `/admin/roles/` нет.
4. **Журнал** — подключил `GET /admin/audit-logs/`, фильтр по `result`, пагинацию сделал на клиенте.
5. **Профиль** — свой аккаунт через `GET /auth/me/`, эффективные права из поля `permissions`.
6. **Пользователи** — пока заглушка с понятным сообщением и ссылкой «Открыть свой профиль».

**Результат:** фронт максимально подогнан под то, что реально есть на бэкенде. То, чего на бэке нет — не падает с непонятной ошибкой, а показывает текст.

### 4.3. Архитектурные решения (почему так)

**Почему без React/Vue:** для учебного проекта второго курса проще объяснить чистый JS. Меньше зависимостей, не нужна сборка.

**Почему отдельный `api-adapters.js`:** бэкенд отдаёт данные в одном формате, а таблице на экране нужен другой. Адаптер — одно место, где это переводится. Если API поменяется — правлю в основном там.

**Почему каталог ролей на фронте:** бэкенд пока не отдаёт список ролей отдельным запросом, а для таблицы он нужен. Взял данные из fixture-файла напарника — ids совпадают с БД.

**Почему наследование только в UI:** в БД хранятся только явные allow/deny. 🕒 считается на фронте для наглядности — так же, как описано в логике бэкенда.

## 5. Сложности и как решал

### 5.1. Бэкенд не совпадал с первоначальным контрактом

**Проблема:** я изначально заложил другие URL и формат JSON (из системной спецификации), а реальный код напарника оказался другим: Token вместо session, POST вместо PUT для матрицы, плоский список вместо сводной таблицы.

**Решение:** прочитал `views.py` и `urls.py` в ветке `feat/back-models-filling`, составил таблицу отличий, переписал `api.js`, `auth.js`, `api-adapters.js`.

### 5.2. API не в той ветке

**Проблема:** в `development` был только фронт и модели, без views.

**Решение:** договорились с напарником о мерже `feat/back-models-filling` → `development`. Пока мержа нет — фронт уже готов к их формату.

### 5.3. Нет эндпоинта пользователей

**Проблема:** страница `users.html` готова, но `GET /admin/users/` на бэкенде не реализован.

**Решение:** не стал делать фейковые данные обратно. Показываю сообщение «недоступно» + ссылку на свой профиль через `/auth/me/`.

### 5.4. CORS и Token auth

**Проблема:** фронт на порту 3456, бэкенд на 8000 — браузер блокирует запросы без CORS. Плюс на бэке не везде настроен TokenAuthentication.

**Решение:** на фронте всё готово. Напарнику передал список: добавить `django-cors-headers`, `rest_framework.authtoken`, настройку `REST_FRAMEWORK`.

## 6. Взаимодействие с бэкендом

Я не писал серверную часть, но для интеграции разобрался, как она устроена:

- модели: `CustomUser`, `CustomRole`, `AppPermission`, `RolePermission`, `AuditLog`;
- права проверяются классом `HasMatrixPermission` — при каждом запросе пишется запись в журнал;
- эффективные права считаются в `calculate_effective_permissions()` с учётом цепочки родительских ролей;
- тестовые роли и правила — в `fixtures/init_data.json`.

Это помогло правильно сделать адаптеры и не сломать логику наследования на UI.
