## 1. Зачем нужен этот фронтенд

Это клиентская часть учебного проекта по RBAC (Role-Based Access Control). Пользователь заходит в систему, после чего может:

- смотреть и редактировать **матрицу прав** (какая роль что может делать);
- смотреть список **пользователей** (когда бэкенд это отдаст);
- читать **журнал доступа** (кто что пытался сделать и разрешили или нет);
- открыть **карточку пользователя** со своими эффективными правами.

Фронтенд **не работает сам по себе** — ему нужен запущенный Django-бэкенд на `http://localhost:8000`. Mock-данных нет, всё тянется с API.

## 4. Страницы приложения

### 4.1. `login.html` — вход

- Форма: логин + пароль.
- При отправке вызывается `auth.login()`.
- Если уже есть токен в `localStorage` — сразу перекидывает на `matrix.html`.
- При ошибке показывает текст под формой (красным).

### 4.2. `matrix.html` — матрица прав

Главная рабочая страница после входа.

- Таблица: **строки** — права (просмотр записей, создание и т.д.), **столбцы** — роли (Пользователь, Менеджер, Аудитор, Администратор).
- В ячейках три состояния при редактировании:
  - **✓** — явно разрешено (`allow`);
  - **✕** — явно запрещено (`deny`);
  - **🕒 насл.** — наследуется от родительской роли (только показ, в БД не пишется).
- Клик по ячейке переключает: пусто → allow → deny → пусто.
- Кнопка **«Сохранить»** активна только если что-то изменилось. Отправляет на бэкенд **только изменённые** ячейки.

### 4.3. `users.html` — пользователи

- Поле поиска (готово под будущий API).
- Таблица: ФИО, логин, роли, статус.
- **Сейчас:** бэкенд не отдаёт `GET /api/admin/users/`, поэтому показывается сообщение «Список пользователей недоступен» и ссылка на свой профиль.

### 4.4. `user.html` — карточка пользователя

- Открывается по адресу `user.html#5` (число после `#` — id пользователя).
- **Свой профиль:** данные и эффективные права через `GET /api/auth/me/`.
- **Чужой профиль:** пока ошибка — на бэкенде нет `GET /api/admin/users/:id/`.

### 4.5. `audit.html` — журнал доступа

- Таблица: время, пользователь, действие, результат (разрешено / отказано).
- Фильтр по результату: любой / разрешено / отказано.
- Пагинация на фронте (бэкенд отдаёт весь список, мы режем по 10 записей на страницу).

### 4.6. Общая шапка

На всех страницах кроме логина:

- логотип RBAC;
- ссылки: Матрица, Пользователи, Журнал;
- кнопка **«Выйти»** — очищает `localStorage` и ведёт на `login.html`.

Активный пункт меню подсвечивается через атрибут `data-page` на `<body>`.

## 5. JavaScript-модули (подробнее)

### 5.1. `auth.js` — авторизация

**Ключ в localStorage:** `rbac_session`

После успешного входа там лежит объект примерно такой:

```json
{
  "token": "abc123...",
  "username": "admin",
  "fullName": "admin",
  "userId": 1
}
```

**Функции:**

| Функция | Что делает |
|---------|------------|
| `getSession()` | читает объект из localStorage |
| `getToken()` | достаёт только token |
| `requireAuth()` | если нет токена — редирект на login.html |
| `redirectIfAuthenticated()` | если уже залогинен — на matrix.html |
| `login(username, password)` | POST `/auth/login/`, потом GET `/auth/me/` |
| `logout()` | удаляет сессию, редирект на login |

**Важно:** бэкенд отдаёт **Token**, а не cookie-сессию. Поэтому каждый запрос в `api.js` добавляет заголовок:

```
Authorization: Token <ваш_токен>
```

### 5.2. `api.js` — слой API

Базовый URL: `http://localhost:8000/api`

Внутри одна функция `request(method, path, body)` — общая обёртка над `fetch`. Если ответ не OK — бросает ошибку с текстом от сервера.

**Методы объекта `api`:**

| Метод | HTTP | Путь | Описание |
|-------|------|------|----------|
| `getMatrixView()` | GET | `/admin/matrix/` | загрузка матрицы |
| `saveMatrixView(...)` | POST | `/admin/matrix/` | сохранение изменений |
| `getAuditLog(params)` | GET | `/admin/audit-logs/` | журнал |
| `getUsers()` | — | — | пока заглушка (пустой список) |
| `getUser(id)` | GET | `/admin/users/:id/` | есть в коде, на бэке пока нет |
| `getMe()` | GET | `/auth/me/` | свой профиль + права |
| `getMyPermissions()` | GET | `/auth/me/` | только права |

### 5.3. `api-adapters.js` — адаптеры данных

Бэкенд и UI говорят на немного разных «языках». Этот файл переводит JSON туда-обратно.

**Каталог ролей и прав** (`ROLES_CATALOG`, `PERMISSIONS_CATALOG`) — скопированы из `backend/rbac_auth/fixtures/init_data.json`, потому что отдельного эндпоинта «дай все роли» на бэкенде пока нет.

**Основные функции:**

- `matrixFromApi(apiRules)` — из плоского списка `{ role_id, permission_id, grant }` собирает таблицу для UI + считает наследование для отображения 🕒;
- `matrixChangesToApi(...)` — сравнивает «было» и «стало», формирует `{ changes: [...] }` для POST;
- `auditFromApi(rows)` — приводит поля журнала к единому виду;
- `effectiveFromMe(me)` — из `{ view_records: "allow", ... }` делает список для карточки пользователя;
- `meToUser(me)` — профиль из `/auth/me/` в формат карточки.

### 5.4. `matrix.js` — логика матрицы

Хранит в памяти:

- `permissions` — список прав (строки таблицы);
- `roles` — список ролей (столбцы);
- `bindings` — текущие значения ячеек;
- `savedBindings` — снимок после последней загрузки/сохранения.

Кнопка «Сохранить» сравнивает только **allow/deny** (наследование в сравнение не входит — оно вычисляется на лету).

### 5.5. `utils.js` — утилиты

- `$()` — короткий alias для `document.querySelector`;
- `renderLoading`, `renderEmpty`, `renderError` — три вида состояния контейнера;
- `formatTime` — время для журнала;
- `statusLabel` — перевод статуса пользователя на русский;
- `setActiveNav` — подсветка активного пункта меню.

### 5.6. `layout.js`

Вызывается на каждой защищённой странице через `initAppShell()`:

1. проверяет авторизацию;
2. вешает обработчик на «Выйти»;
3. подсвечивает текущую страницу в меню.

## 6. Как фронт общается с бэкендом

### 6.1. Вход

```
POST /api/auth/login/
Body: { "username": "...", "password": "..." }

Ответ 200: { "token": "..." }
Ответ 400: { "error": "Неверный логин или пароль" }
Ответ 403: { "error": "Ваш аккаунт заблокирован..." }
```

После этого фронт сам делает:

```
GET /api/auth/me/
Header: Authorization: Token ...

Ответ: {
  "id": 1,
  "username": "admin",
  "is_blocked": false,
  "permissions": {
    "view_matrix": "allow",
    "save_matrix": "allow",
    ...
  }
}
```

### 6.2. Матрица

**Загрузка:**

```
GET /api/admin/matrix/
```

Ответ — массив:

```json
[
  { "id": 1, "role_id": 1, "permission_id": 1, "grant": "allow" },
  ...
]
```

**Сохранение:**

```
POST /api/admin/matrix/
Body: {
  "changes": [
    { "role_id": 2, "permission_id": 3, "grant": "allow" },
    { "role_id": 2, "permission_id": 5, "grant": "none" }
  ]
}
```

`grant: "none"` — убрать явное правило (вернуться к наследованию или отсутствию права).

### 6.3. Журнал

```
GET /api/admin/audit-logs/?result=allow
GET /api/admin/audit-logs/?result=deny
GET /api/admin/audit-logs/?user_id=1
GET /api/admin/audit-logs/?date_from=2026-01-01&date_to=2026-06-01
```

Ответ — массив:

```json
[
  {
    "id": 1,
    "username": "admin",
    "action": "view_matrix",
    "result": "allow",
    "created_at": "2026-06-16 12:00:00"
  }
]
```

## 7. Роли и права (справочник на фронте)

Пока бэкенд не отдаёт справочники отдельными запросами, на фронте зашиты такие данные:

**Роли:**

| ID | Название | Родитель |
|----|----------|----------|
| 1 | Пользователь | — |
| 2 | Менеджер | Пользователь |
| 3 | Аудитор | — |
| 4 | Администратор | — |

**Права:**

| ID | Codename | Название в UI |
|----|----------|---------------|
| 1 | view_records | Просмотр записей |
| 2 | create_records | Создание записей |
| 3 | delete_records | Удаление записей |
| 4 | view_audit | Просмотр журнала логов |
| 5 | export_audit | Экспорт логов |
| 6 | manage_roles | Управление ролями |
| 7 | view_matrix | Просмотр матрицы прав |
| 8 | save_matrix | Сохранение матрицы |

Если на бэкенде добавят новые права — их нужно будет дописать в `PERMISSIONS_CATALOG` в `api-adapters.js`.

## 8. Наследование прав (как показывается 🕒)

Бэкенд в матрице хранит только **явные** правила (allow/deny). Наследование считается на фронте для удобства:

1. Берём роль с родителем (например, Менеджер → родитель Пользователь).
2. Если у Менеджера **нет** своего правила на право X, но у Пользователя стоит **allow** — в ячейке показываем 🕒 «насл.».
3. При клике наследование не сохраняется в БД — пользователь задаёт своё allow/deny или сбрасывает в none.

Это совпадает с логикой бэкенда: если записи в `RolePermission` нет, `calculate_effective_permissions` идёт по цепочке родителей.

## 10. Как запустить локально

### Фронтенд

Из папки `frontend/`:

```bash
npx serve . -p 3456
```

Открыть в браузере: http://localhost:3456/login.html

Можно и через Live Server в VS Code — главное, чтобы JS-модули грузились (нужен локальный сервер, не `file://`).

### Бэкенд (кратко)

Нужна ветка с API (`feat/back-models-filling` или после мержа в `development`):

```bash
cd backend
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py loaddata init_data.json
python manage.py createsuperuser
python manage.py runserver
```

Пользователя нужно создать и назначить роль **Администратор** (через Django admin), иначе матрица и журнал вернут 403.

### Если фронт на другом порту

На бэкенде должен быть включён CORS, например:

```
Access-Control-Allow-Origin: http://localhost:3456
```

Иначе браузер заблокирует запросы.

## 11. Типичные ошибки

| Сообщение / поведение | Причина |
|-----------------------|---------|
| «Ошибка 403» на матрице | у пользователя нет `view_matrix` / `save_matrix` |
| «Failed to fetch» | бэкенд не запущен или CORS не настроен |
| «Сервер не вернул токен» | на бэке не подключён `rest_framework.authtoken` |
| Пустой журнал | ещё не было обращений к защищённым эндпоинтам |
| Список пользователей пустой | эндпоинта пока нет — это ожидаемо |

## 12. Как менять адрес API

```javascript
export const API_BASE = 'http://localhost:8000/api';
```

Для другого сервера достаточно поменять хост/порт.
